# Спецификация: CS2 reverse trade-up planner

## 1. Цель продукта

Сайт помогает собрать trade-up контракт CS2 под конкретную цель: пользователь выбирает желаемый скин и его float, а сервис:

1. находит допустимую структуру контракта;
2. вычисляет, какие float нужны у входных предметов;
3. учитывает уже имеющиеся у пользователя скины;
4. ищет реальные лоты на Steam Market;
5. выбирает наиболее дешёвый набор лотов, который даёт нужный результат;
6. отдаёт готовые 5 или 10 предметов для покупки и крафта.

Ориентир по классу продукта — [FloatJitsu](https://www.floatjitsu.com/), но основной сценарий сайта — обратный поиск: **от желаемого результата к конкретным предметам для покупки**.

## 2. Что пользователь должен получить

Пользователь задаёт:

- целевой скин;
- желаемый float: точное значение, максимум или диапазон;
- обычный/StatTrak режим;
- опционально: уже имеющиеся предметы и их inspect links;
- дельту `δ` — допустимое отклонение при поиске float лотов на Steam Market;
- опционально: бюджет и приоритет «самый дешёвый» / «самый точный float».

Сайт возвращает:

- шанс получить целевой скин и полный список альтернативных исходов;
- прогноз float и состояния износа для каждого исхода;
- 5 или 10 конкретных входных предметов с exact float, ценой и ссылками на Steam Market;
- итоговую стоимость, отклонение от target float и подтверждение, что выбранный набор соответствует расчёту;
- ближайший достижимый результат и объяснение, если исходная цель недостижима.

## 3. Ключевые правила CS2

- Обычный контракт: 10 скинов одной редкости → 1 скин следующей редкости.
- Контракт ножа/перчаток: 5 Covert → 1 exceedingly rare предмет; поддерживается отдельным режимом.
- Входы могут быть из разных коллекций, если у каждой есть предмет следующей редкости.
- Нельзя смешивать обычные и StatTrak-предметы.
- Float **не влияет на вероятность выпадения названия скина**. Он влияет только на float/износ каждого возможного исхода.
- Вероятность исхода задают состав коллекций и число исходов следующей редкости:

  `P(исход) = входов из коллекции / число входов в контракт × 1 / число исходов следующей редкости в этой коллекции`.

- Для контракта из одной коллекции с 1/2/3/4 равновероятными исходами шанс каждого — 100%/50%/33,33%/25%.

## 4. Математическое ядро

У каждого скина есть свой допустимый диапазон `[min, max]` (float cap). Поэтому raw float нельзя усреднять напрямую.

Для каждого входного предмета:

`adjusted_i = (float_i − min_i) / (max_i − min_i)`

`adjusted_i` — относительный износ: `0` — самый чистый возможный экземпляр данного скина, `1` — самый изношенный. То есть индивидуальный диапазон скина растягивается в универсальную шкалу `0–1`.

Для контракта из `n` предметов (`n = 10` или `5`):

`avg_adjusted = Σ adjusted_i / n`

Для каждого возможного исхода:

`out_float = out_min + avg_adjusted × (out_max − out_min)`

Обратный расчёт для выбранного target float:

`target_avg_adjusted = (target_float − target_min) / (target_max − target_min)`

Задача оптимизатора: найти допустимые входы, для которых `avg_adjusted` попадает в требуемый диапазон, и при этом вероятность целевого скина соответствует ожиданию пользователя.

## 5. Функциональные требования

### FR-1. Каталог и проверка допустимости

- Хранить для каждого скина: коллекцию, редкость, качество, StatTrak-совместимость, `min/max float`, список возможных trade-up исходов.
- При выборе цели показывать, из каких входов её можно получить и с каким шансом.
- Валидировать контракт до расчёта: редкость, коллекции, число предметов, StatTrak и режим 5/10 предметов.

### FR-2. Reverse-калькулятор

- По целевому скину и target float рассчитывать `target_avg_adjusted`.
- Подбирать типы входных скинов и exact float для всех слотов.
- Поддерживать цель «точный float», «не выше X» и «в диапазоне [A, B]».
- Показывать достижимость: exact / в пределах допуска / ближайший достижимый / невозможно.
- Для каждого предложенного крафта показывать вычисления, все исходы, их вероятность, float и состояние износа.

### FR-3. Частично собранный крафт

- Пользователь добавляет уже имеющиеся предметы через inspect link.
- Сервис получает их actual float, фиксирует занятые слоты и пересчитывает, какое `avg_adjusted` должны дать оставшиеся предметы.
- Сервис подбирает только недостающие слоты.

Пример: у пользователя есть 5 `M4A1-S | Knight` с известными FN-float и он хочет `AWP | Dragon Lore` в заданном FT-float. Сайт должен посчитать точные float 5 недостающих Knight и подобрать реальные экземпляры, а не ограничиться советом «купить BS Knight».

### FR-4. Поиск и оптимизация лотов Steam Market

- Для каждого требуемого входного скина получать ограниченную выборку лотов Steam Market — стартовый лимит: до 200 кандидатов.
- Получать exact float каждого кандидата по inspect link/проверке базы; витринной маркировки FN/MW/FT недостаточно.
- По требуемому float `f` и дельте `δ` искать кандидаты в диапазоне `[f − δ, f + δ]`, с учётом float cap.
- Искать не только лот, ближайший к идеальному float каждого слота, а оптимальную комбинацию всех 5/10 лотов по ограничению итогового `avg_adjusted`.
- Среди допустимых комбинаций выбирать наименьшую по суммарной цене; при равной цене выбирать наиболее близкую к target float.
- Выдать пользователю финальный список: название, exact float, отклонение, цена, ссылка на покупку, сумма и проверенный прогноз результата.
- При замене одного лота автоматически пересчитывать требования к остальным слотам и новую оптимальную комбинацию.
- Если подходящего набора нет среди 200 кандидатов: предложить увеличить `δ`, обновить выборку или показать самый близкий реально собираемый крафт.

### FR-5. Объяснение рисков и ценности

- Показывать отдельно: шанс целевого названия, float целевого исхода и итоговую стоимость. Не смешивать эти показатели.
- Показывать все нежелательные исходы с их вероятностями и float.
- Рассчитывать суммарную цену, комиссии, ожидаемую стоимость (EV), прибыль/убыток и, при наличии данных, ликвидность.

## 6. Требования к точности и edge cases

- Вычисления должны эмулировать `float32` IEEE 754, включая промежуточные округления, а не полагаться на JavaScript `number`/`float64`.
- Хранить и выводить: внутренний `float32`, отображаемый десятичный float, состояние CS2 и расстояние до ближайшей границы FN/MW/FT/WW/BS.
- На границах состояний показывать предупреждение: округлённый float может выглядеть как один wear, а внутреннее значение дать другой.
- Проверять такие случаи по полученному Steam Market exact float/inspect link,
  отображаемой категории и прогнозу сервиса; не подменять источник сторонним
  marketplace.
- Есть неподтверждённая гипотеза, что порядок добавления предметов в контракт влияет на крайние результаты из-за неассоциативного суммирования `float32`. Для пограничных крафтов сохранять порядок слотов и валидировать перестановки на реальных контрактах. До подтверждения не обещать пользователю, что порядок меняет результат.

## 7. План реализации

Статус на 26.07.2026: математическое ядро, полный versioned каталог, reverse
подбор normal Covert-путей, Steam listing provider и collector UI завершены.
Обычные тесты детерминированы: они используют фиксированные source bytes/SSR
fixtures и не открывают локальный TCP или внешнюю сеть. Невыполненные пункты
ниже требуют либо provider реальных объявлений, либо подтверждённых данных из
игры — они не считаются закрытыми без таких данных.

### Этап 1 — данные и математический прототип

1. [x] Собрать каталог скинов, коллекций, редкостей и float caps: полный
   versioned ByMykel snapshot materialize-ится в runtime catalog; caps сверяются
   с Valve data.
2. [x] Реализовать `float32`-формулы: нормализацию, расчёт исхода и обратный расчёт.
3. [ ] Набрать проверочные кейсы по **фактическим** контрактам; UI/API
   collector, обязательная evidence URL, provenance каталога, content ID без
   дублей, preview float32 bits и progress dashboard готовы, но реальные
   evidence-записи не подменяются fixture.
4. [x] Реализовать расчёт вероятностей исходов по составу коллекций.

**Результат этапа:** пользователь вводит цель и вручную заданные входы, сервис точно рассчитывает все исходы, их float и вероятности.

### Этап 2 — reverse-подбор крафта

1. [x] Реализовать поиск допустимого normal-пути коллекции для Covert-цели.
2. [x] Реализовать exact float для 10 слотов и режим частично заполненного
   контракта: без listing provider возвращается `ideal_math`, с fixture pool
   перебираются реальные кандидаты этого тестового набора.
3. [x] Добавить интерфейс с объяснением математики, шансов и недостижимости цели.
4. [x] Добавить форму для evidence-backed фактического контракта: 10 inputs,
   предварительный расчёт, actual output и progress набора.

Ограничение этапа: 5 Covert → knife/gloves и reverse-пути к не-Covert целям
ещё не materialize-ятся, так как для них нужна отдельная versioned модель
outcome pools.

**Результат этапа:** сервис предлагает идеальный математический крафт, даже без связи с маркетом.

### Этап 3 — Steam Market и реальные покупки

1. [x] Получать до 200 active Steam Community Market лотов на каждый
   допустимый input через server-side HTML/SSR parser с кэшем, pagination и
   rate limit. Лимит применяется к каждому skin, не к контракту целиком.
2. [x] Получать exact raw float из Steam asset property `2` и inspect link из
   `market_actions` + property `6`; произвольные owned inspect links остаются
   отдельным адаптером этапа 4.
3. [x] Оптимизировать набор real listings по цене и точности: до 28 кандидатов
   используется точный перебор, для большего пула — bounded beam search без
   повторного использования одного listing.
4. [x] Отдавать 10 purchase/inspect ссылок и пересчитывать корзину при новом
   запросе плана. UI показывает статус provider и свежесть cache.
5. [~] Normal Steam flow проверен как отдельный live-путь в desktop приложении. Для StatTrak provider
   фильтрует только exact `StatTrak™` market hash и не подмешивает normal-лоты,
   но публичная SSR group-страница пока не даёт подтверждённого отдельного
   StatTrak filter; нужен регулярный live regression smoke-test.

**Результат этапа:** пользователь получает реально покупаемый набор предметов для крафта.

Live Market включён в настройках desktop-приложения, но требует одноразового
подтверждения перед первым запросом. Steam key, cookie и CSFloat API не
требуются. Режим можно отключить для офлайн-математики. Provider читает текущую
публичную SSR-разметку Steam Market, поэтому операция зависит от
недокументированного формата и лимитов Valve. Кэш и rate limit обязательны для
бережного polling. Без provider результат намеренно остаётся `ideal_math`, а не
искусственной ценовой корзиной.

Тестовая граница Steam изолирована: production fetcher читает live SSR HTML,
а обычные Rust-тесты подают в parser/pagination/cache фиксированные HTML
страницы через in-memory fetcher. Live-проверка выполняется вручную из UI с
явным включением Market.

### Этап 4 — ценность и надёжность

1. [ ] Добавить комиссии, EV, прибыль/убыток и ликвидность.
2. [~] Collector реальных контрактов реализован в UI и API; он требует
   публичную evidence URL, показывает preview float32 bits, сохраняет версию
   каталога и детерминированно отклоняет повтор той же evidence-backed записи.
   Собрать подтверждённый набор для постоянной проверки формулы после обновлений
   CS2 ещё предстоит.
3. [ ] Исследовать edge case порядка слотов и добавить поддержку только при воспроизводимом подтверждении.

### Следующее действие

Набрать через UI как минимум 20 evidence-backed фактических контрактов с
bit-exact совпадением, намеренно покрыв границы FN/MW/FT, разные float caps и
перестановки одинакового набора входов. Каждая новая запись должна содержать
публичную evidence URL и автоматически сохранит версию каталога, использованную
для расчёта. Регулярно запускать `./scripts/smoke-steam-market.sh` (включая
отдельный StatTrak smoke-test после подтверждения фильтра), так как формат
Market не является API. Параллельно нужен отдельный versioned unusual/loot
mapping для 5 Covert → knife/gloves.

## 8. Критерии готовности MVP

- Для заданного target skin + target float сервис находит допустимый контракт или честно сообщает, почему он невозможен.
- Расчёт совпадает с проверочными фактическими контрактами в пределах подтверждённой точности `float32`.
- Пользователь видит вероятность целевого названия отдельно от float результата.
- При наличии 5 уже имеющихся предметов сервис подбирает остальные 5.
- Для найденного крафта пользователь получает 10 конкретных лотов с Steam Market, их exact float, цену и подтверждённый итоговый расчёт.
